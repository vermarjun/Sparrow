# Dogfood log: building "no group chat" with Sparrow (17 Oct 2026)

First real run of Sparrow building Sparrow. Captain = the user's Claude Code session.
Each entry: what happened, impact, suggested fix.

## Setup

1. **`bin/sparrow` runs straight from `src/`.** Agents edit the repo that their own reporting CLI
   loads, so a half-written edit in `src/cli` or `src/shared` breaks every agent's `sparrow done`.
   Worked around with a git worktree (`../sparrow-nogroup`). Fix: ship a built/pinned CLI, or have
   `sparrow up` snapshot the CLI it puts on agents' PATH.
2. **Resume descriptions don't match their config.** `builder` says "Claude Code, Opus" but runs
   `sonnet` at effort xhigh; `builder-codex` says "gpt-6.1-sol" but runs `gpt-6-luna`; `verifier`
   says "(Codex)" but runs OpenCode `deepseek-v4.1-flash` at effort `low`, which is a weak model
   for an adversarial verifier. Fix: render harness/model in `sparrow resumes` from config only,
   drop model names from descriptions, and lint description vs frontmatter in `sparrow doctor`.
3. **Worktree has no `web/node_modules`.** Fresh worktrees need `bun install` in `web/` before
   the UI builds. Minor; mention in captain skill's worktree advice.

## During the build

4. **The captain never saw @leo's progress.** Leo posted 4 updates (15:40–15:43); they went to
   the group thread and the captain's `inbox --wait` only returned the final result. This is the
   exact gap the feature fixes; good baseline for comparing after the change.
5. **Running `sparrow` from a worktree registers a phantom project.** `sparrow log @leo` from
   `../sparrow-nogroup` registered a new captain in a new project `sparrow-nogroup` (git
   toplevel basename) and said "No messages". Fix: resolve project from the *main* worktree
   (`git rev-parse --git-common-dir`), so worktrees of one repo share a project.
6. **Track B finished in ~4 min but over-applied the spec**: pasted the same "quiet updates"
   paragraph into all six resumes, duplicating protocol.md in every system prompt; missed
   `web/test/format.test.ts` because the brief said "don't touch test/" (ambiguous with
   `web/test/`). Captain brief issue, not a harness issue; sent back via DM (resumed the same
   Codex session fine).
7. **Full system prompt and task are in process argv.** `pgrep -fl "sparrow inbox"` matches
   every agent (their prompts mention the command), so a careless `pkill -f` by a captain would
   kill agents. Also leaks prompts into `ps`. Fix: launch scripts already cat files; pass
   `--append-system-prompt-file`/config files where the harness supports it.
8. **Captain foot-gun: a detached `sparrow inbox --wait` silently eats messages.** Any process
   calling `/api/inbox` as the captain marks deliveries delivered; a stray background poller
   (output to /dev/null) would lose results with no trace. Fix idea: `sparrow inbox --peek`, or
   keep delivered messages re-readable via `sparrow inbox --since <seq>`.
9. **The captain overrode the owner's model choice, and Sparrow let it.** The captain hired
   @maya with `--model opus` (resume `builder` is configured `sonnet`), reasoning from the resume
   *description*. `sparrow hire --model/--effort` and `HireReq.model/effort` exist, and the
   captain skill advertises them ("override the resume"); `core.hire` does
   `req.model ?? resume.model`. This defeats the point of resumes as the owner's cost control.
   Fix (next change): remove `--model`/`--effort` from `sparrow hire`, `HireReq` and the captain
   skill; the server ignores/rejects them. Resume frontmatter is the only source of model/effort.
   Also correct entry 2: a description/config mismatch is something to report, not to "fix" with a flag.

## Fix list (after this feature)

- [ ] **Lock model/effort to the resume.** Remove `--model`/`--effort` from `sparrow hire`
      (`src/cli/main.ts:29`), drop `model`/`effort` from `HireReq` (`src/shared/types.ts`), make
      `core.hire` use `resume.model`/`resume.effort` only (`src/server/core.ts:334-335`) and
      reject requests that still send them (400, "model and effort come from the resume"), and
      delete the "override the resume" line from `assets/skills/sparrow-captain/SKILL.md:38`
      and DESIGN §5. Test: a hire with `model` in the body is refused. (Entry 9.)
- [ ] **Captain skill: pipeline verification, don't idle.** The captain sat waiting on @maya while
      @leo's finished track sat unverified, with 2 of `max_running` 3 slots free; the owner had to
      prompt it. The skill has no guidance on concurrency beyond "extra hires show queued". Add:
      "verify each finished track as soon as it lands (hire a verifier) while others still work;
      check `sparrow status` for free slots (`max_running`, default 3) before deciding to wait."

10. **The configured verifier was good.** @iris (OpenCode, deepseek-v4.1-flash, effort low)
    verified track B in ~5 min with a clean PASS/FAIL table and caught 4 real doc
    contradictions (stale §11 A1/A4, §3.10, the captain skill's message kinds) that the builder
    and the captain missed. This supersedes the "weak model" worry in entry 2: the owner's cheap
    config did the job.

11. **Agent env leaks into the test suite.** On untouched `main`, `bun test test/` run *inside an
    agent window* fails 1 test (launch.test.ts) because the agent shell exports SPARROW_URL /
    SPARROW_HOME / SPARROW_AGENT_ID for the live server. Every agent that builds Sparrow must
    remember `env -u …`. Fix: a test preload that clears SPARROW_* (except ones a test sets), or
    a `bun run test` script that does it.
12. **Captain-mode piggyback consumed the wake.** Maya found that every captain CLI call first
    registers, and the register response piggybacks the inbox; with quiet deliveries this would
    have made `inbox --wait` return instantly on a mere update. Fixed in track A (only a waking
    message skips the long-poll). Consider making register never piggyback.
13. **Timeline:** hire 15:40 → track B done 15:44 (fix rounds 15:45, 15:55) → verified 15:56;
    track A done 15:58 (18 min, Opus override). Verification started at 15:5x only after the owner
    prompted the captain (see fix list).
14. **Verifier caught a bad check in the captain's brief.** @nina (same cheap config as @iris)
    ran the full suite, a live isolated server with the fake harness, a v2→v3 migration
    experiment, and a cited code review in ~6 min. It flagged that my check 2a ("must print No
    new messages") contradicted the spec (updates posted during the window are rightly shown at
    timeout) instead of failing the code. Its stale-group-delivery edge case: 0 such rows in the
    live DB.
15. **Totals:** 4 hires (2 builders, 2 verifiers), 3 follow-up DMs to @leo, 1 re-verify. Every
    resume/DM round-trip worked first time (Codex resume, OpenCode resume). No crashes, no
    nudges, no "stopped without reporting".
